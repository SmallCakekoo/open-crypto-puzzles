## The puzzle, in one paragraph

34 numbered panels, each a movie still, in fixed panel order. Transform each
title "somehow" into an English BIP39 word -> 34 words. Drop exactly 10
"intruders" using information on each film's IMDb page -> 24-word mnemonic in
panel order -> derive a Bitcoin address -> must equal the escrow
`bc1q94ecsn0qk8lap2gefrycnms3ruepy889z969a6` (100,000 sats, funded 2022, still
unspent). Full rules and sources: `README.md`, `clues/author-posts.md`.

**The user's stated priority for whatever comes next: any further large-scale

## What was tested this session (all negative -- read before repeating)

Full blow-by-blow is in `analysis/tested.md` (long, chronological, dated
entries) -- this is the summary.

1. **Single-field sweep** (~24 fields this session, on top of ~25 more from a
   2026-08-04 pass documented in `README.md`): country (single vs
   co-production), language, certificate, color/B&W, genre count, genre
   identity, runtime, budget, gross, distributor, production-company count,
   writer-credit-block count, won-an-Oscar, nominated-for-Oscar,
   sequel/reboot/spin-off status, aspect ratio, first-listed genre,
   IMDb-keyword "Franchise" category presence (checked live on all 34 films'
   `/keywords/` pages, not from memory), rating score, vote count, decade of
   release, one-word-vs-multi-word title. **None gives exactly 10 with a
   natural reading and no exceptions.** Vote count did hit exactly 10 at one
   cutpoint but is disqualified on principle, not just data precision: IMDb
   vote counts grow every day, so a puzzle mechanism based on them could never
   be stably reproducible from 2022 (when the escrow was funded) to now to
   whenever someone else tries to solve it.
2. **"Shares X with another panel" relational fields** (the same structure
   that made H1 work before it was falsified, tried with other fields):
   production company (19 flagged), distributor (17), writer (2). None = 10.
3. **Two-field boolean combinations**: 24 single-field criteria crossed
   pairwise with AND and OR (600 tests). 17 land on exactly 10 -- flagged to
   the user as almost certainly multiple-comparisons noise (expected by chance
   alone at that many trials). Only one had a genuinely single-concept natural
   reading rather than an arbitrary pairing: **"single country of origin AND
   single language"** (a purely domestic, monolingual production) -- flags
   these 10 as intruders: Close Encounters of the Third Kind, Escape from
   Alcatraz, Ghostbusters II, Mad Max, Scream 2, Sharknado, Spartacus, Star
   Wars: A New Hope, The Crimson Rivers, Toy Story 2. **This is the closest
   thing to a "leading hypothesis" right now, but it has NOT been derivation-
   tested with the newest literal-substring finds (see below) and the other 16
   noise-hits have not been derivation-tested at all.**
4. **End-to-end derivation attempts against the country+language-split
   hypothesis**, using `tools/oracle.py`'s `check()` directly (imported
   in-process, fast): first pass 6,912 candidates (0 matches), widened to
   169,344 by cross-referencing each zero/tied-candidate panel's *actual* IMDb
   keyword list against real BIP39 words (0 matches), widened again to
   38,896,200 by doing the same for the 6 tied-literal panels too -- **this
   final 38.9M-candidate run was executed by the user locally with
   `analysis/bruteforce_country_lang_split_mp.py` (multiprocess, verified
   correct against `itertools.product` before running) -- 0 matches,
   confirmed complete.** This does not disprove the hypothesis (only 24-word
   candidates *actually built from IMDb-sourced or literal words* were tried;
   the true word for any under-determined panel could still be something not
   surfaced), but the "obvious" word space for this specific 10-intruder split
   is exhausted. **Not yet re-run with the new literal substrings found after
   this run** (run, guard, term, load, tip -- would grow the space to roughly
   1.07 billion, explicitly not run yet, paused per the user pending a
   decision on whether/how to pursue it, see "priority" above).
5. **Word-property numerology** (word length, word's alphabetical index in the
   BIP39 list): tried per the user's suggestion, found near-hits (e.g. index
   <1024 splits 18/10 among the 28 panels with a determinate word) but
   explicitly rejected as invalid candidates for two reasons: (a) 6 panels
   (now 5, after finding "art" for Spartacus) had no determinate word so any
   split computed this way is not really "10 of 34," and (b) a word's position
   in the BIP39 list is not "information on the film's IMDb page," which is
   what the puzzle's own rules text says the intruder criterion must use --
   this would violate the puzzle's premise, not just fail a statistical bar.

## Operational notes

- **Windows PowerShell/Bash tool + venv**: the project venv is at
  `C:\Users\Usuario\Desktop\open-crypto-puzzles\.venv`. Use
  `.venv\Scripts\python.exe` explicitly (not bare `python3`, which lacks
  `bip_utils`) for anything touching `tools/oracle.py`.
- **IMDb blocks `WebFetch` with HTTP 403** (Cloudflare/AWS WAF). Use the
  interactive Browser tool instead. It geo-localizes to Mexico by default
  (Spanish UI, MX-specific release dates/ratings) unless you set cookies first:
  `document.cookie = "lc-main=en_US; domain=.imdb.com; path=/"` and
  `document.cookie = "international-seo=us; domain=.imdb.com; path=/"` via the
  browser's JS-exec tool, then reload. Do this once per fresh browser session
  before trusting any IMDb page content (release dates, certificate, etc. are
  wrong otherwise).
- **Large brute-force runs**: the user ran the final 38.9M-candidate search
  locally with 12 workers while also on a video call, and the machine had what
  sounded like a serious freeze/hard-reboot partway through (unresponsive,
  stuck cursor). Plausibly thermal/stability related to 12 cores at 100% for
  ~14 minutes concurrent with call load. **Recommend leaving 1-2 cores of
  headroom (`--workers <cpu_count-2>`) for any future large parallel run, and
  avoid running one during a call.** The multiprocess script
  (`analysis/bruteforce_country_lang_split_mp.py`) is reusable as a template --
  it verifies its own index arithmetic against `itertools.product` before
  trusting it, worth keeping that pattern for any new large search.
- `analysis/tested.md` is long now (many hundred lines) -- when adding to it,
  append new dated entries at the end rather than trying to read the whole
  file first; same for `analysis/leads.md`.

## House rules this whole investigation has followed (keep following them)

- Never invent a word or accept a criterion because it "would be convenient" --
  every accepted candidate/criterion traces to either a literal substring
  check against the real 2048-word BIP39 list, or a sourced, independent piece
  of evidence (an IMDb-listed keyword/review, a documented portmanteau, a
  character name actually in the cast list -- not free-associated from
  memory).
- A checksum-valid BIP39 mnemonic is not evidence of anything by itself. Only
  a derived-address match against the escrow counts as a solution.
- A field that hits exactly 10 by itself is not evidence either, once you've
  run enough trials (600 two-field tests produced 17 coincidental hits this
  session) -- multiple-comparisons noise is real and already bit this project
  once before (the vote-count "hit," the word-index-parity "hit").
- When the user provides a new identification or correction, verify what you
  can before accepting it, and say plainly when something is "user's own
  claim, not independently verified by me" vs. "independently sourced."
- Document everything in `analysis/tested.md` (negatives ledger) and
  `analysis/leads.md` (open leads, non-literal candidates) as you go, append
  don't rewrite, and say explicitly what a new finding invalidates and what it
  leaves standing.
